## 错误 #1：正则表达式全局替换导致括号损坏

- **现象**：在对 `03_结果与分析.md` 执行第3轮正则批量括号削减时，规则 `re.sub(r'），', '，', content)` 将"）后紧跟，"的所有模式替换为"，"，导致18个闭合括号被误删，文件出现大量不匹配的左括号`（`
- **根因**：该正则匹配的是所有"），"模式，但目标仅应为"以）结尾的插入语后的逗号"。正则编写时未考虑"），"中的"）"可能属于不应删除的括号对（如实验编号引用、数值标注等），属于过度匹配。更根本的问题是没有在批量正则执行前进行受影响的括号语义分类
- **影响范围**：03_结果与分析.md —— 约18处数据标注括号损坏（涉及行47, 59, 85, 93, 97, 99, 101, 103, 115, 117, 123, 125等），括号配对失衡；03章未被git跟踪，`git checkout` 无法回滚
- **修复措施**：逐行定位每个不匹配的`（`，通过18次独立 Edit 调用手动补回每个`）`，耗时约30分钟
- **预防红线**：
  1. **批量正则操作前必须先 `git add` 暂存当前版本**，确保有快速回滚路径
  2. 禁止使用匹配边界不明的删除类正则（如 `re.sub(r'），', ...)`），改为精确的完整括号内容替换
  3. 任何正则替换后必须**立即验证括号配对**（`count('（') == count('）')`），发现不匹配立即中止并回滚
  4. 对于文本修改类任务，**优先操作已git跟踪的文件**；未跟踪文件先提交初版再编辑

## 错误 #2：Python语法错误——全角括号误入代码

- **现象**：`_reduce_parens.py` 第187行报 SyntaxError：`m3(（"..."` 使用了全角 `（` 而非半角 `(`
- **根因**：在编写 `MORE_03` 规则列表时，频繁切换中英文输入导致全角括号混入函数调用
- **影响范围**：脚本无法执行，阻塞了第3轮替换
- **修复措施**：将 `m3(（` 修正为 `m3((`
- **预防红线**：
  1. 在编辑器中启用**全角/半角符号可视化**（如显示不可见字符）
  2. 写完Python代码后运行 `python -c "compile(open('file').read(), 'file', 'exec')"` 做语法预检
  3. 中文内容用变量或数据文件存储，代码中仅使用ASCII字符

## 错误 #3：变量定义顺序错误——NameError

- **现象**：运行 `_reduce_parens.py` 时 NameError: `MORE_03` not defined
- **根因**：`MORE_03` 规则列表定义在 `if __name__ == "__main__": main()` 块之后，而 `main()` 函数中引用了 `MORE_03`。Python在函数调用时才解析全局变量，但 `main()` 被调用前 `MORE_03` 尚未定义
- **影响范围**：03章第2轮替换无法执行
- **修复措施**：将 `if __name__ == "__main__": main()` 移至文件末尾
- **预防红线**：
  1. 所有模块级变量定义**必须在任何引用它们的代码之前**
  2. 遵循标准文件结构：imports → constants → functions → `if __name__ == "__main__"`
  3. 使用 linter（如 pylint/flake8）做静态检查可提前发现此类错误

## 错误 #4：长中文字符串导致 Write 工具 JSON 解析失败

- **现象**：使用 Write 工具直接写入含大量中文内容（数千字符）的文件时，工具返回 JSON 解析错误
- **根因**：工具调用参数需经 JSON 编码传输，长中文字符串中包含的特殊字符（换行引号、全角符号等）在序列化/反序列化过程中导致 JSON 结构破坏
- **影响范围**：01章和03章的部分写入操作需要重试
- **修复措施**：改用 Bash heredoc 方式（`cat << 'PYEOF' > file`）绕过 JSON 编码层直接写入
- **预防红线**：
  1. 写入超过500字符的中文内容时，**优先使用 Bash heredoc** 而非 Write 工具
  2. 或在 Write 前将内容保存为临时变量，分段写入
  3. 写入后立即 Read 验证内容完整性

## 错误 #5：文件被linter自动修改导致编辑冲突

- **现象**：在执行 Edit 工具修改文件内容时，target 文件被 IDE linter 自动格式化，导致 `old_string` 匹配失败
- **根因**：IDE的自动格式化功能在文件保存后触发，改变了空白符/换行等格式，使 Edit 工具的精确匹配条件被破坏
- **影响范围**：多次 Edit 调用需要先 Re-read 获取最新内容后才能成功
- **修复措施**：每次 Edit 失败后重新 Read 文件获取linter修改后的最新版本，再重试
- **预防红线**：
  1. 大批量编辑任务前，**临时禁用 IDE 自动格式化** 或使用 `--no-format` 模式
  2. Edit 调用失败时，先 Read 确认当前文件状态，不要连续重试相同 old_string
  3. 对格式化敏感的文件，使用 Write 全量覆写替代多次 Edit

## 错误 #6：未跟踪文件无法git回滚

- **现象**：03_结果与分析.md 在 git 中处于 untracked 状态，执行 `git checkout -- 03_结果与分析.md` 时报 "did not match any file(s) known to git"，无法通过 git 回滚括号损坏
- **根因**：03章为本次会话新创建的文件，尚未 `git add`，不属于版本控制范围
- **影响范围**：括号损坏后无法快速回滚，被迫手动逐处修复（耗时约30分钟）
- **修复措施**：手动通过 Edit 工具逐处修复每个被错误删除的 `）`
- **预防红线**：
  1. **新文件创建后立即 `git add`**，即使不做正式提交，也确保工作区有版本快照
  2. 对尚不稳定的文件，创建手动备份副本（`cp file.md file.md.bak`）
  3. 批量修改操作前执行 `git status` 确认所有目标文件已受版本控制

## 错误 #7：工具调用参数格式包装导致功能异常

- **现象**：使用 `__unparsedToolInput` 包装 Edit 工具参数时，工具无法正确解析输入，编辑操作静默失败
- **根因**：`__unparsedToolInput` 是框架内部数据结构，不应用于直接工具调用；包装后参数解析层无法识别
- **影响范围**：若干次 Edit 操作无效，浪费了调用次数
- **修复措施**：放弃包装器，使用标准工具调用格式
- **预防红线**：
  1. 仅使用框架文档明确支持的参数格式
  2. 不要使用 `__` 前缀的内部/未公开参数结构
  3. 工具调用失败时检查参数格式是否标准，而非盲目重试

## 汇总统计

| 错误类型 | 次数 | 严重程度 | 可预防性 |
|---------|:----:|:-------:|:-------:|
| 正则过度匹配 | 1 | 🔴 高（数据损坏） | ✅ 可预防 |
| 语法错误（全角符号） | 1 | 🟡 中（阻塞执行） | ✅ 可预防 |
| 变量顺序错误 | 1 | 🟡 中（阻塞执行） | ✅ 可预防 |
| 工具兼容性问题 | 3 | 🟢 低（需重试） | ⚠️ 部分可预防 |
| 版本控制缺失 | 1 | 🔴 高（无法回滚） | ✅ 可预防 |
| linter编辑冲突 | 1 | 🟢 低（需重试） | ✅ 可预防 |

**核心教训**：对未受版本控制的文件执行批量破坏性操作，是本会话中最危险的行为。正则替换在文本处理中威力巨大但风险同样巨大——"先备份、再操作、立即验证"应成为肌肉记忆。
